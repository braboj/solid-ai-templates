# ADR-029: A changelog adopted late records earlier versions by reference

## Context

`base-docs` requires `CHANGELOG.md` of any project that publishes
versions. This repository publishes versions — 65 tags and 64 GitHub
Releases from `v2.1.0` to `v2.63.0`, each with notes generated by
`--generate-notes` — and carried no such file. The check that shipped
with the rule printed `no CHANGELOG.md - nothing to check` and exited
clean, so the breach was silent.

Two questions had to be answered before the file could be written, and
they produce different work.

The first is whether a per-version record published by the code host
discharges the requirement. Generated notes are derived from merged pull
request titles. Their entry form is therefore whatever those titles were:
no Added/Changed/Fixed grouping, no bound on length, and no statement of
what a reader must do. The rule's own content is precisely what generated
notes do not provide.

The second follows from answering the first "no". A project with 64
published versions and no changelog then owes entries for all of them,
and the only machine-readable source for that history is the pull request
titles — the form just rejected. Reconstructing from them would produce a
file that satisfies the check while failing the rule's premise, which is
worse than the absence, because an absence is visible and a plausible
wrong file is not.

## Decision

1. **Hosted notes do not discharge the requirement** — a project that
   publishes versions MUST carry a committed `CHANGELOG.md`. A release
   page is where the record MAY additionally be published, never where it
   MAY instead live. The committed file is present in a clone, a mirror,
   a vendored copy and an offline archive, and is versioned alongside the
   code it describes.

2. **A project adopting the changelog late starts at the next version** —
   its first section is the version being released next. Earlier versions
   are recorded by naming where they are published, as a closed set that
   does not grow.

3. **Reconstruction from pull request titles is forbidden** — the
   reviewer-facing form is what the rule rejects, and a file of it passes
   the check while failing the rule.

4. **Every version released after adoption gets its own section** — the
   reference covers history, never the present.

## Alternatives considered

- **Generated notes discharge the requirement** — rejected; it empties
  the rule for every project using them, which is most projects on a code
  host. A pull request title is written for a reviewer holding the diff; a
  changelog entry is written for someone outside the project deciding
  whether to upgrade.
- **Reconstruct all 64 versions from the release notes** — rejected;
  the source is the rejected form, and the result would satisfy the
  40-word check while consisting of reviewer-facing titles. It also
  fabricates a record no one wrote at the time.
- **Scope the rule so this repository is already conformant** — rejected
  as special pleading. The rule is right; the repository was in breach,
  and the fix belongs on the repository side.
- **Leave the changelog absent and track it** — rejected; the breach was
  already tracked and the tracking is what surfaced the question. Filing
  it again defers the same decision.

## Consequences

- `templates/base/core/docs.md` states that hosted notes do not discharge
  the requirement, carries the adoption clause, and its check now
  distinguishes a project that has published nothing from one that has
  published versions and has no changelog. Both previously printed the
  same skip.
- The check's measurement unit changes from the physical line to the
  entry. A word bound measured per line is defeated by wrapping — the
  first changelog written against this rule had three entries of 45, 41
  and 42 words that the line-based measurement reported as none.
- `templates/base/core/git.md` gains a changelog-completeness check and
  names the changelog in the release sequence. Both release variants are
  renumbered to carry the added pre-release step.
- This repository carries `CHANGELOG.md`, opening at `Unreleased` and
  naming the GitHub Releases for `v2.1.0` through `v2.63.0`.
- `docs/PLAYBOOK.md` gains the cut as release step 4, before the tag;
  its later steps and audit table are renumbered.
- A consuming project that already publishes versions inherits an
  obligation it can discharge without fabricating history.
